Measured on `main` 750af6c (v0.55.0-construct-words) with the new probe, then after each fix.

## The machine (Brent's desktop - the one the game is played on)

| | |
|---|---|
| CPU | AMD Ryzen 9 9950X, 16 cores / 32 threads |
| GPU | NVIDIA GeForce RTX 4080, 16 GB (driver 32.0.16.1088 / 610.88); the CPU's Radeon iGPU is present and unused |
| RAM | 128 GB (4 x 32 GB DDR5, running at 3600 MT/s) |
| Screen | 1920 x 1080 at 74 Hz |
| OS | Windows 11 Pro 10.0.26200 |
| Engine | Godot 4.7.2 standard, Forward+, **Vulkan 1.4** on the RTX 4080 (the engine log says so; not D3D12, whatever the 4.6 default notes say) |

## How it is measured

`game/tests/perf_probe.tscn` (see its header and CLAUDE.md "Performance"): the whole game (main.tscn) in one busy
scene, a scripted invulnerable player (the `bot` flag), enemies too tough to die so the fight lasts, **windowed
1920 x 1080 (borderless, the screen's size), vsync off, no frame cap**, 4 s of warm-up then 12 s measured. One
`PERF scene=...` line per run and `PERF: PASS / FAIL` against `game/data/perf_budget.json` (60 fps average, 60 fps
1% low, <= 2000 draw calls, <= 2048 MB working set, no frame over 33.3 ms while measured nor in the warm-up after
the build frame). `tools/perf/perf_all.sh` runs every scene at the default zoom (0.5) and the furthest (0), three
times each, one Godot at a time, and `tools/perf/perf_median.py` prints the medians below.

Scenes: **wall** - the passage's last wall (13 real bodies: 7 grunts, 3 brutes, the commander, 2 archers), the player
steps in a second into the warm-up and the wall wakes as in play (`spawn_ms` is that frame); **stubble** - by the
tree camp with it, the sounder and the herd awake and fighting; **town** - walking a loop through the ten
townsfolk; **nether** - the Stubble's Netherecho at the dry well, the projection out, six constructs on it, wisps;
**skills** - wall 10 again, hit every 0.45 s by six area skills of six affinities in turn (Slag Pool, Whiteout,
Forked Path, Teeming Fog, Cave-In, Drench): zones, a cloud, chains, delayed blasts, a dozen statuses.

Columns: frame rate (average, 1% low = the mean of the slowest 1% of frames), frame time (average, worst), the
renderer's own CPU and GPU times, the frame's `_process` and `_physics_process` steps (every script), draw calls
(average, most), triangles drawn (shadow passes included), the working set at the end, hitches (frames > 33.3 ms
while measured), and in the warm-up: hitches, the worst frame and the wall's spawn frame.

Other agents' Godot runs and tools ran on the same machine at the same time (the shared lock serialises the Godot
runs, not everything else); each number is the median of three runs, and runs agreed within a few percent.

**Verdict on the baseline.** On this machine the average frame rate is five to seven times the 60 fps target in every
scene but one, and the draw calls are inside 2000 everywhere. What fails:

1. **The wall's spawn frame: ~390 ms.** Not the bodies' build (~2 ms each once their kind is loaded) but the first
   build of each kind: loading the female body model, each kind's garments, props and textures - 67-767 ms per kind
   the first time (headless bench: grunt 767 incl. the male body, archer 558 incl. the female body, commander 222,
   brute 136, harrier 118, pavise 75, drummer 68, censer 67). In play every new kind's first wall stalls like this,
   and so does a commander's call for help.
2. **The skills scene: 1% low 46 fps, 3-4 hitches of ~40 ms, 1953 draw calls.** With the HUD switched off
   (`--no-hud`) the same scene runs 317 fps average and 1065 draw calls (wall: 572 fps, 929 draws): **the HUD, redrawn

3. The Netherecho had one warm-up hitch (83-100 ms) in two of six runs.

## Fixes, biggest first, and what each bought

### 1. Bodies loaded with the level and built ahead; one glow pass; unseen pieces dropped; numbers fade cheaply

Four changes measured together (commits 30d69d3, 14660ba, e4e235e); what each bought is told apart by what it
touches:

- **Load every enemy kind with the level, build the next wall's bodies ahead** (main.gd `_warm_bodies`,
  `_prebuild_bodies`; `Models.prebuild`). The passage and the arena load every kind they can put up in their own
  loading frame, and the next wall's (or wave's) bodies - and whoever a commander calls - are built one a frame
  while you walk or rest. **Wall spawn frame 391 -> 12.5 ms**; the wall's first seconds have no hitch left.
  The load moved to entering the passage (once a session: about 2 s the first time, all kinds).
- **The glow pass only while it glows** (`RealCharacter._show_overlay`). Every piece of every body was drawn
  twice, the second time as an invisible additive overlay. **Wall: triangles 2.44 M -> 1.59 M, draw calls
  1144 -> 1030**; town 495 -> 448.
- **Settled looks drop the pieces they never show** (`RealCharacter.strip_hidden`, enemies and townsfolk):
  ~115 meshes per body down to the 9-17 it wears. **Nodes: wall 2589 -> ~1220, town 1607 -> 569.**
- **Combat numbers fade by transparency, not by recolouring** (FloatText): a Label3D rebuilt its mesh every frame
  for every number in the air.

### 2. The effects' shaders held from boot; the HUD's skill numbers cached (826cece, a6c7ac8)

- **Effect shaders held** (main.gd `_hold_effect_shaders`). The skills scene's last hitch was Cave-In: ~20 ms
  inside its cast, every time (`--trace`). Bisected with a scratch bench: building the blast's ring cost 20 ms
  whenever no other blast was on the ground, and 0.1 ms when one was. Godot builds a StandardMaterial3D's
  shader lazily, when its RID is first asked for, shares it among the materials with the same features, and
  frees it when the last of them goes - so a short-lived effect whose feature set nothing else uses compiled its
  shader again each time it appeared (bench: a new unshaded alpha material 20-21 ms with no live sibling, 0.03 ms
  with one). Main now keeps one material of each feature set the effects use, with its RID asked for at boot, so
  those shaders are made once while the game starts and never thrown away.
- **The HUD's slot numbers cached** (hud.gd `_slot_stats`). Every hotbar slot ran `Player.ability_stats` every
  frame - a deep copy of the skill's data and, with a sealed word, the rune engine. Now only when the skill's
  state, the affinities or worn gear's cost change. (The HUD's `_draw` measured 2.7 ms a frame with six skills and
  a status-laden pack; the dock was 1.2 ms of it.)

### A first run on a fresh machine (no shader cache)

The numbers above have the shader cache on disk (`user://shader_cache`) warm from earlier runs, as every run after
the first will. To see the very first run, the probe was run with the cache switched off
(`rendering/shader_compiler/shader_cache/enabled=false` in a temporary `game/override.cfg`): wall 360 fps / 1% low
230, skills 145 / 80, Stubble 307 / 170 - all PASS, no hitch while measured or in the first seconds. Compiling
shaders lands in the level's own load: the build frame grows (wall 1.2 s, Stubble 2.8 s) and the second frame
after it takes 99-163 ms (the first draw of everything). That is loading, not play; a loading screen would hide it.

### What is still over, or close, and why

- **The Stubble and the Netherecho: one frame of 36-128 ms in the first seconds, in some runs** (2 of 6 and 1 of 6
  above; the baseline had the same: 34 and 83-100). Both scenes are the Stubble zone; it is not every run, so it is a
  background job finishing (most likely the 240 x 160 m zone's navigation bake being swapped in, LevelNav) rather
  than anything a frame always does. Traced after merging main (`--trace=30`, three Stubble runs): one run had a
  100 ms frame 0.29 s in, of which the scripts took 2 ms (process 0.6, physics 1.3) - the time is spent outside the
  scripts (the engine's own step or the renderer), consistent with the zone's navigation bake being handed over.
  Not fixed; the next thing to look at for the Stubble (LevelNav's swap-in, or drawing everything for the first time).
- **Draw calls in a skill storm: 1916 at most** (budget 2000). About 700 of them are the HUD (the same scene with
  `--no-hud`: 1065), which is redrawn from GDScript every frame: one draw call per text run, polyline and chip of the
  enemy bars, status chips, orbs and dock. Making the HUD keep what does not change (the dock, the orbs' frames) as
  separate, rarely redrawn canvas items is the next lever; not done here (the HUD is 1,544 lines and has its own
  click tests).
- **The HUD's frame cost** on a status-laden pack: ~2.7 ms of GDScript (`_draw`) plus the canvas it builds, the
  biggest steady cost left in a fight (wall 572 fps without it, 363 with).
- **Memory**: the working set rose ~110 MB (1.45 -> 1.56 GB on the wall) because one body of every kind is now kept
  loaded and ready. VRAM is 1.35-1.5 GB: the 205 character textures are imported *lossless* (uncompressed RGBA); VRAM
  compression (BC7) would cut that several-fold, but it is a re-import of 165 MB of art and a look change to check -
  left for the minimum-spec pass (Phase 7).

### Not done, on purpose

- **Visibility ranges / LOD and shadow distance**: the GPU takes 0.9-2.4 ms a frame here; nothing to buy on this
  machine, and both change what is seen at the edge of the view. Worth it on a weaker GPU (Phase 7).
- **Pooling combat numbers**: with the mesh rebuild gone they no longer show in the traces.
- **Gameplay**: untouched. The wall's kinds, order and placement are the same (`_wall_kinds` / `_wave_kinds` are
  the old inline lists); bodies are built earlier, not differently.

### After merging main (8d9a113: saves, physics pin, build stamp, seeded tests, the suite in the repo)

- The probe again (windowed, one run each): wall 365 fps / 1% low 231, skills 154 / 85, Stubble 303-312 / 166-178,
  Netherecho (far) 303-316 / 185-205 - the same as before the merge. `bash tools/test/run_all.sh --all`: **ALL PASS,
  23 tests** (logs kept outside the repo).
- **No gameplay change.** The combat timeline probe gives byte-identical output on main and on this branch. The newbie
  duels give identical singles; their multi-enemy rows (pairs, camps, the herd) differ from run to run *on main itself*
  (two runs of main differ in 3 rows, two runs of this branch in 13), even with RngSeed: those fights depend on
  something besides the seed (frame timing, most likely). Every row is a win either way; this branch's second run
  matches main's earth and fire camp rows exactly. Worth knowing for anyone comparing duel numbers: compare singles,
  or several runs.
