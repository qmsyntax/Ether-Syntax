# Ether Syntax (working title; was "Passage") — an action RPG inspired by the "1% Lifesteal" universe

Brent's own game, inspired by how the 1% Lifesteal world works and its power system, with the author's informal
blessing (see rule 1). Not a licensed or official adaptation. Process framework: Claude Code Game Studios
template (MIT, see `.claude/LICENSE-ccgs`), adapted. Owner / product lead / lore authority / playtester: Brent.

## Project rules (these override anything in the template)

1. **What we may use.** The series belongs to Robert Blaise (publisher: Aethon Books). Brent asked him, and on
   2026-10-22 he answered (`production/outreach/2026-10-19-robert-blaise/reply-2026-10-22.md`): a game *inspired by*
   the 1% Lifesteal universe is fine, using **how the world works and the power system**; **not** the story or the
   characters. It is not a licence: any official adaptation begins on his side, so never present Ether Syntax as the official
   1% Lifesteal game.
   - Use freely: the world's workings and the power system (stars, essence and reflux, talents and primes, the
     ethercosm and Netherecho, constructs, passages and realms, runes). Lean into setting-faithful tone and mechanics.
   - Never: the story, plot events or canon characters. Player characters, NPCs, talents' wording, names and art are original.
   - Never store, paste or reproduce book text. No bulk downloads, no DRM stripping, no piracy sites. Work from
     paraphrased mechanics notes with chapter citations (`research/`), fan sources, and Brent's recollection.
   - Nothing is published or distributed, and nobody is contacted, unless Brent explicitly asks. Whether the books'
     coined terms keep their names in a public release is decided then.
2. **Provenance tags are mandatory** in design docs: `[C]`/`[CANON]` read directly, `[F]` fan source, `[B]` Brent's ruling, `[MODEL]` our invention, `[?]` unknown. Brent's rulings override fan sources. See `design/01-systems-bible-v0.md`.
3. **Say what was and wasn't tested.** A headless run proves scripts load; it does not prove a mechanic works or feels right. Anything that needs hands on the controls is reported as "untested — needs Brent". Never claim a feature works on the strength of it compiling.
4. **The first real gate is fun, not paperwork.** The core-loop questions in `design/03-core-mechanics-spec-v0.1.md` §8 are answered by Brent playing the build. The author would like to see it; the vertical slice is the natural thing to show him, when Brent says.
5. **Talents are data** (`game/data/talents.json`), many and varied — 1% Lifesteal is one entry, not the premise.

## Technology Stack

- **Engine**: Godot 4.7.2 (standard build, installed via winget — no `godot` alias on PATH; use `open-editor.cmd`, or the console exe under `%LOCALAPPDATA%\Microsoft\WinGet\Packages\GodotEngine.GodotEngine_*\`)
- **Language**: GDScript, statically typed
- **Godot project root**: `game/` (this is `res://`). The template's `src/` and `assets/` conventions map to `game/scripts/` and `game/data/` until `/adopt` decides otherwise.
- **Version Control**: Git, trunk-based on `main`, pushed to the private GitHub repo `qmsyntax/Ether-Syntax` (remote `origin`, SSH). See "Version Control" below.
- **Smoke check**: `--headless --path game --import`, then `--headless --path game --quit-after 400 -- --shot` must produce no `ERROR` / `SCRIPT ERROR` lines.
- **Tuning numbers live in `game/data/*.json`** (`balance.json`, `enemies.json`, `abilities.json`, `talents.json`) and are read through the `GameData` autoload. No numeric gameplay constants in scripts — structural constants (layer names, colours, panel sizes) are the only exception.
- **Damage goes through the hook pipeline.** `Player.deal_damage()` and `take_hit()` build a `HitContext` and run it through every `TalentEffect` in `player.effects` (`on_outgoing`, `on_dealt`, `on_incoming`, `on_reflux_cap`, `on_tick`, `on_ascend`, `status_lines`). A talent is `game/scripts/talents/<id>.gd` extending `TalentEffect`, loaded by id. Items, summons and tempering techniques will be effects too. Never branch on `talent_id` in gameplay code.
- **Interface** lives in `game/scripts/ui/` plus `hud.gd`. `UiTheme` holds the palette, serif font and the Theme applied at `ui_root` (parent of the HUD and every screen); `UiDraw` holds the procedural drawing (orbs, rings, bars, glyph icons); `UiWidgets` the small reusable controls; each screen extends `UiScreen`, owns no game state and calls public methods on `main.gd`. No image assets - everything is drawn. Use `set_anchors_and_offsets_preset`, never `set_anchors_preset`, for full-rect controls (the latter preserves a zero size). Every UI change is verified with `--shot-ui=title|town|town-gate|town-folk|town-talk|skill-tree|skill-tree-field|stations|craft|craft-done|craft-item|shop|saves|inventory|hud|hud-low|hud-dual|temper|ethercosm|nether|create-1..5` (windowed; saves `shots/shot.png`) and `--shot-settings`, and the images are looked at.
- **Character art** is procedural: `game/scripts/art/models.gd` (`Models.player()`, `.enemy(kind)`, `.scenery(kind)`, `.pickup(equippable)`) plus `.weapon(item_id)`, `.projection()`, `.wisp(affinity)`, `.construct(tier, concept)` (`nether_models.gd`), builds `ModelRig`s from procedural meshes (`MeshKit`) - no image or mesh assets. The look is grounded dark fantasy (art pass 3): realistic proportions, muted worn materials, one accent per character; the matching lighting (filmic, SSAO, light fog, low sun) is set in `main.gd` `_build_world` / `_set_nether_look`. The equipped weapon is shown with `ModelRig.set_weapon`. Enemy models are in `art/enemy_models.gd` (grunt, brute, commander, archer, harrier); each has a wind-up pose of its own (the archer's draw, the harrier's crouch) and enemies are fought from behind as well as in front, so backs are designed too. Gameplay scripts own a rig and drive it through `set_highlight`, `flash`, `set_windup`, `set_staggered`, `set_part_visible`, `set_dead_look` and `animate(delta, speed, attacking)` (poses only ease in while `animate` is being called); collision and gameplay sizes still come from data, not from the model. Designs must be original. Preview every model with `res://tests/art_preview.tscn -- --shot` (and `--shot=close`), which saves `shots/art-preview.png` / `art-close.png`.
- **Character creation** is `ui/creation_screen.gd` (steps: Origin, Appearance, Prime, Skills, Embark; a SubViewport turntable in the middle). It builds a draft `spec` {name, identity, look, talent_id, affinities, skills} and calls `main.begin_character(spec)`, which refuses a spec without exactly `skill_tree.json` "start_picks" (2) root skills of the prime's affinities. A look is a Dictionary of option ids; gameplay and UI reach the model library's options only through `CharacterLook` (`options`, `normalize`, `cycle`, `build`), and the options themselves are defined in `art/player_look.gd`. The identity (Man / Woman) sets the look's `sex`, which changes the body and face; options hidden for a sex are listed in `creation.json` `hidden_options`. `set_zoom(close)` frames the face. Identities, name pool and option labels are in `data/creation.json`; affinities and which ones a prime carries in `data/affinities.json` (+ optional `affinities` on a talent). Verify with `--shot-ui=create-1..5` and the windowed click test `res://tests/creation_probe.tscn` (must print `CREATE: PASS`; it picks two skills by clicking and checks nothing else is given).
- **Affinities** (`data/affinities.json`): water, fire, earth, wind, lightning, each with a colour and a three-ability `kit` (projectile, melee_burst, dash). Affinities are NOT tied to the talent (Brent 2026-10-11): they decide which skills can be learned and are rolled per prime. Character creation offers three rolled primes (`PrimeRoll`: talent off a weighted table, 1-3 affinity slots - one common, two rare, three very very rare - each filled at random; numbers in `balance.json` "primes"). `Player.set_affinities` gives the character its affinities and, as a sandbox loadout for tests, shots and bots, their whole kits; a real character then gets exactly its two picked skills from `Player.start_with_skills` (no skill is given automatically - Brent 2026-10-18); `prime_default` (water) is only for tests, bots and old saves. Reflux is per affinity (`reflux_by`, `locked_by`, `reflux_of()`, `is_locked()`); `reflux` / `reflux_locked` are shorthand for the first affinity only. An ability can only be cast if the character holds its affinity. Wisps in the Netherecho carry an affinity and only attuned ones can be gathered. Tint anything affinity-related with `GameData.affinity_color()`. Verify dual-affinity HUD with `--shot-ui=hud-dual`.
- **Skills** (design/05, approved 2026-10-12; step 1 built: water and lightning). A skill's `kind` in `abilities.json` picks its behaviour in `Player.cast_ability`: `projectile`, `melee_burst`, `dash`, `beam`, `targeted_strike`, `blink`. Everything a skill does to an enemy goes through ONE function, `Player.apply_hit(target, payload, tags, stage_mult, dir)`, fed a hit payload from the data (`on_hit` / `on_pass` / `on_arrive`: damage or damage_mult, status, shove, marks, interrupts) - add effects there, never inside a behaviour. Statuses live on the enemy (`add_status`, `status_stacks`, `stun`, `interrupt`, `shove`; rules in `data/statuses.json`). Water shoves, and a shove that ends against a wall, block or body is a Crush (`Player.on_crush`, numbers in `balance.json` "shove"). Lightning leaves Live marks; the third is an Overload (`_add_marks`, `_overload`). Affinity-specific reflux rules are keys on the affinity (`reflux_shed_mult_combat`). Skills that need a target or a landing spot are checked BEFORE essence is spent. A skill has a recovery (`abilities.cast_recovery` or its own) during which nothing else can be cast; running hot lengthens it and no longer hurts. Move things by exact distance (`move_and_collide`, swept checks), not by velocity: `move_and_slide` picks its own time step outside a physics frame, which made a shove overshoot and a dash skip an enemy. Fire is built (step 3a): Heat - an affinity with `damage_per_reflux` multiplies every hit tagged with it by `Player.heat_mult(aff)`, measured at the moment of impact; Alight - a status that burns in the name of whoever applied it (`add_status(id, stacks, by)`), spreads to an enemy that stands close, and jumps on death; a `targeted_strike` may `consume_status`; a `dash` may leave a `trail` (`GroundZone`) and `stops_at_bodies`. The player's dash, like a shove, is moved by exact distance. Wind is built (step 3b): Slipstream - `player.pips`, earned from distance actually travelled (`_tick_slipstream`, numbers in `balance.json` "slipstream") and spent by wind skills (`spend_pips`); Lee - an affinity's `rear_bonus` on a hit to the back; a skill tagged `rear` always counts as from behind; wind's reflux sheds by movement (`reflux_shed_mult_moving` / `_standing`); Aloft status (light enemies only - heavier ones lose poise). Projectiles (`projectile.gd`) fly by exact distance through `tick()`, stop on walls, strike nearest-first and may `pierce`. Earth is built (step 3c), so all five starter kits are: any skill may carry a `windup` - `cast_ability` takes the cost at once, holds the cast in `player._windup` and `_tick_windup` lets it go through `_perform_cast` (the one place a skill's effect happens); you are rooted and aimed until then, and `braced` skills make you Braced (`is_braced`, `balance.json` "braced"). Standing stone is `scripts/stone.gd` (`Stone`, group `stones`, a StaticBody3D on layer 1 once up, so it blocks walking, rays and every shot): `player.raise_stone`, `player.stones`, `Stone.shatter(dir)`, `Stone.way_round()` (how enemies get past it - stone is not in the navigation mesh), numbers in `balance.json` "stone"; the `prop` kind raises one at the cursor. `player.cursor_fixed` points the cursor for a test. Verify with `--shot-ui=skills`, `--shot-ui=fire`, `--shot-ui=wind` and `--shot-ui=earth`. Step 4 enemies: `enemies.json` kinds pavise, censer, drummer and the phased commander; behaviours `support` (`_think_support`) and `commander` (`_think_commander`) in `enemy.gd`; `scripts/censer_burst.gd`; an enemy asks for help with the `reinforcements` signal, which `main._on_reinforcements` answers; `player.shove()`. `--shot-ui=enemies4` shows them. Step 5a: skills outside the kits are learned from scroll items (`items.json` kind `scroll`, `player.read_scroll` / `can_learn` / `learn`, `Inventory.is_loot`); skill kinds `displace`, `delayed_blast` (`scripts/delayed_blast.gd` -> `player.land_blast`), `detonate`, `chain`. In tests, `_cast(p, id)` casts by id and `player.cursor_fixed` aims. Step 5b: kinds `ground_zone` (`scripts/ground_zone.gd`, strips and circles), `self_buff` (`player.buffs`, read where each matters: `take_hit`, `deal_damage`, `is_braced`, `buff_num`), `rod` (`scripts/ground_rod.gd`, `_rod_relay`); a dash may be `braced` with `on_stop`. Step 5c (the five held skills: channel, charge_release) is not built. In tests, `_foe` cannot be staggered; use `_fighter` when poise is the subject. A screenshot state must not force a tooltip over the thing it exists to show.
- **Equipment** (design/06, approved 2026-10-12; step 1 built). Slots are `Inventory.SLOTS`, the twelve of design/06 section 2: weapon (main hand), offhand, ranged, head, body, hands, feet, back, belt, satellite, trinket, trinket2 (`slot_kind` / `slots_for` / `slot_for`; `equip(id, into)`; trinket2 takes `trinket` items and the same item is never worn twice). The inventory screen is a paper doll (`ui/inventory_screen.gd`: sheet, figure with a slot column either side via `FigureView`, pack grid, a description panel that compares against what is worn; abilities are its second tab; `--shot-ui=inventory` and `inventory-abilities`). A stat is read from every slot through `inventory.stat()` except the `melee_*` ones, which `weapon_stat()` reads from the main hand only. `armour` on worn gear is the percent taken off each hit (`Player.armour()`, capped by `balance.json` "gear"); it and tempering come off a blow BEFORE talents see it, so a talent that delays or multiplies a hit works on the reduced number. The ranged weapon is fired with the held `ranged_stance` action (Shift) plus the strike button: `Player.fire_ranged(point)`, no essence, numbers in `balance.json` "ranged" and on the item (`ranged_damage_mult`, `ranged_interval`, `ranged_range`). In the stance the strike button never walks or strikes. `design/data-drafts/items-v2.json` is the DRAFT catalogue and is not loaded; bring items over step by step, and do not put a stat on a live item until the game reads it. Tests that assert an exact amount of damage taken call `_bare(p)` to remove the starting coat.
- **Combat rules** (design/05 section 6, step 2 built; numbers in `balance.json` "combat"). Enemies (`enemy.gd`) have a `facing` that turns at a limited rate, so `is_behind()` / `is_in_front()` mean something; `poise` (`take_poise`, `stagger`); a `behaviour` of `melee` | `ranged` | `pouncer`; and a `telegraph` dictionary the HUD draws (slam circle, aim line, white = interruptible). Defender-side rules live in `enemy.take_hit` (front armour, staggered takes more); attacker-side rules live in `Player.deal_damage` (rear hit, Opening on a staggered enemy for a bare strike, working reflux off, poise damage). `interrupt()` breaks a wind-up; `interrupt_attack()` is what an interrupting skill calls and also staggers a flagged attack. Melee enemies must hold a slot (`Player.claim_slot`, six at a time) to close in. Heavy blows stagger the player (`is_staggered()`). A movement skill commits you (`dash_recovery_s`) and a second one too soon costs double (`winded`). The passage adds enemies per wall from `passage.wall_recipes`. Pathfinding (2026-10-18): every level gets a `LevelNav` (`scripts/level_nav.gd`, added in `main._add_level_nav`) that bakes two navigation meshes from the level's static colliders on layer 1 (radius 0.5 for the common walker and the bot, 1.0 for brute and commander), in the background, and rebakes by itself when a static body is added to or removed from the level (a doorway sealed or opened); numbers in `balance.json` "navigation". Enemies and the bot follow paths with `NavPath` (`enemy._route_dir`, the archer's `_find_vantage` / `_seek_line`, the drummer, `player._bot_way`); standing stone is not baked in and is walked round with `Stone.way_round()` (the open end). Until a level's first bake lands, and in unit-test worlds without a `LevelNav`, the old steering applies: `Route.step_toward` through a doorway via the `router` group (`main.route`). A new obstacle only needs a StaticBody3D on layer 1 under the level. Debug-draw the mesh with `--shot-ui=nav` (or `nav-<biome>`); `--nav-timing` prints each bake's cost. Use `_dummy_enemy` (no armour, no poise) for arithmetic tests and `_fighter` for behaviour. When a bot run times out it prints where the bot and every surviving enemy are - read that before guessing. Verify with `--shot-ui=combat`.
- **Health** (`body.gd`, Brent 2026-10-11): one health bar plus wounds. A wound cuts the bar's ceiling (`total_max()`) while it lasts and has a hidden `sink` that healing must fill before it closes; the sink is never drawn in the bar and never shown as a number (`Body.wound_state` gives words). Natural healing refills the bar only. A night's rest fills sinks of wounds marked `natural` (never `lost_arm`); the healer works on the oldest wound; talent healing follows `player._spend_heal_points` (one star: sinks then bar; two stars: bar to half, sinks, bar). Wound rules and numbers are in `balance.json` "wounds", "talent_healing", "healer", "night". There are no superficial / structural / catastrophic layers any more; `Body.missing()` ignores its argument.
- **Tempering techniques** (`data/tempering.json`, `ui/tempering_screen.gd`, the `# --- tempering` block in `player.gd`): passive, all active at once, stage + 0-100% progress, stage cap stars + 1. A character knows the plain one plus one per affinity held. Training is a session in the town's tempering yard that leaves a `temper_strain` wound. Multiplier effects are read through `player.temper_stat(stat)`; `max_health` effects change `body.max_hp` when a stage is gained (and are already inside a save's `body`). Abilities do not hurt their caster by default (Brent 2026-10-11) - `self_harm` is an optional ability key that nothing uses.
- **Biomes** (`scripts/art/biomes.gd` and one `biome_<id>.gd` each: scrubland, dungeon, snow, swamp, mountain, city): `Biomes.info(id)` (look, prop list, scatter table), `.floor`, `.wall`, `.prop`, `.gate`. `main.gd` builds every level from the current biome (`_use_biome`, `_biome_floor`, `_biome_wall`, `_scatter_props`, `_spawn_cuttable`); colliders are separate unseen boxes, the kit only draws. Which biomes a delve, the arena and the town use, prop counts and wall heights are in `balance.json` "biomes". Blocking props still hug a side wall and keep apart (they were placed that way before there was pathfinding; enemies now path round them, but open-floor blockers have not been tried in the passage). Force a biome with `--biome=<id>` (works with the bots) and screenshot one with `--shot-ui=biome-<id>`; every biome must pass `--bot-dungeon --biome=<id>`.
- **The Netherecho** lives in `game/scripts/nether/` (`Netherecho` controller owned by `main.gd`, one per level; `projection.gd`, `nether_construct.gd`, `wisp.gd`, `NetherArt`). It is driven by `nether.tick(delta, camera)` only while a projection is out; the body is parked by `player.projecting`. Numbers are in `balance.json` "nether" and `constructs.json` "wild". Wild constructs are the only source of constructs. World picking shared with the player is in `Pick`.
- **Controls are InputMap actions** defined in `game/scripts/keybinds.gd` (autoload `Keybinds`), one binding each, saved to `user://keybinds.cfg`. Never read raw keys in gameplay code — use `Input.is_action_pressed` / `event.is_action_pressed`, and build on-screen prompts from `Keybinds.binding_text()` so they follow rebinds. Number-key menu choices are the one exception. `--shot-settings` (windowed) screenshots the controls menu.
- **Passage bot runs**: `--headless --path game -- --bot-dungeon`, `-- --bot-full` and `-- --bot-die` must each print `PASS` (exit code 0). A scripted, invulnerable, overpowered player walks the assault passage: leaving at the first exit, clearing all ten walls, and dying inside. They prove the seal, wall activation, barriers, exit unlock, spoils arithmetic (the exit pays items, counted at their value) and the live death path (wake naked in town, corpse left in the passage); they say nothing about difficulty or feel. `--shot-dungeon` (windowed) saves a screenshot of wall 2 to `shots/`.
- **Skill points and the skill tree** (design/08, Brent 2026-10-18; numbers and the tree in `data/skill_tree.json`, read through `GameData.skill_tree` / `skill_node` / `skill_tree_of` / `skill_roots`): a new character picks two root skills; the rest are trained. Points: `player.skill_points`, earned in `grow_star` (`_earn_skill_points`, one per `points.per_star_pct` of growth, banked in `skill_growth`) and on ascending; both are saved. One tree per affinity: tier 1 = the kit, tier 2 hangs off one root, tier 3 needs either of two; `requires` is any-one-of. `Player.cannot_train_reason` / `train_skill` (points + fee + prerequisites + `can_learn`'s affinity rule) and `cannot_drill_reason` / `drill_skill` (progress only, never a stage). Only `main.train_skill` / `drill_skill` call them, and only while talking to the trainer in town; scrolls (`read_scroll`) still teach anywhere with no points or prerequisites. `ui/skill_tree_screen.gd` (key `skills`, L, or from the soul screen) can be looked at anywhere; Learn and Drill work only when the trainer opened it (`at_trainer`).
- **The town is a place** (design/08; `data/town.json`, `scripts/town_builder.gd` `TownBuilder`, `scripts/townsperson.gd` `Townsperson`): state `"town"` is a walkable city level built like a zone; the player is active there and casts nothing. One townsperson per service (real bodies dressed from data, fixed look seed, a `Label3D` name plate): healer, merchant (shop + sell loot), innkeeper (room, save/load, new character, ledger), trainer, tempering yard master, corpse clerk, passage ticket clerk. Walk up and press `interact` (F), or click them (`main._town_click` walks you there): `main.talk_to(role)` opens `ui/talk_screen.gd` (`TalkScreen`, their services + the ledger). A screen they open (shop, yard, tree, register) closes back to them; walking further than `leave_reach` closes it all. Gateways: the Dross Gate and the arena gate are walked through (`_tick_town`); the passage door is shut and used with interact (ticket). `_enter_town(arrive)` places you by where you came from (`town.json` "arrive"). There is no town menu any more.
- **Crafting step 1** (design/12; rules design/11 section 4; Brent 2026-10-18: no star cap, full sale price): band-1 Rendering, Leatherwork and Smithing. `game/data/crafting.json` is GENERATED by `tools/items/emit_crafting_game.py` from the design drafts (rules as numbers in `tools/items/crafting_tables.py` `CRAFT_NUMBERS`) - edit the drafts or tables and re-run, never the JSON; `GameData.crafting`, and its items join `GameData.items` without overriding a live id. Rules in `scripts/crafting.gd` (`Crafting`: `chance`, `why_not`, `combine(p, rid, ctx, rng)`, `teach`); state on the player (`craft_skill`, `craft_known`, `craft_made`, `tool_uses`, saved). Where you may combine is main.gd's: `main.craft(rid, ctx)` only at the station of the keeper you are talking to (`open_crafting`, `open_station_shop`, `learn_trade`) or on a field kit in the pack (`open_field_kit`). Stations are `town.json` "stations" (models in `art/station_models.gd`); `ui/craft_screen.gd`. Tools, kits and materials are not "loot" (not bulk-sold) and sell at full value one at a time; gear and scrolls keep `gear_sell_factor`. No world clock yet: combines take no game time. Shots: `--shot-ui=stations|craft|craft-done|craft-item`.
- **Money (Brent 2026-10-18)**: nothing pays cash. A kill drops its kind's `remains` (`enemies.json`); the passage exit gives `spoils` items (`items.json`, `main.grant_spoils`) up to what you can carry; money comes only from selling in town. No rent except a room at the inn and an owned passage's ticket and meter. Death: `player.die_to_corpse` + `respawn_naked`; corpses are saved on the player and laid back in their level by `main._place_corpses`; retrieval is a flat `town.corpse_fee_per_star` x stars.
- **Overland zones (design/07)**: `data/zones.json`, built by `ZoneBuilder` (`scripts/zone_builder.gd`) from `main.enter_zone(id, arrive)`; state `"field"`, `main._tick_field`. Map-frame coordinates (origin north-west, x east, y south) -> level frame with `ZoneBuilder.to_local`; `main.zone_point` goes back. The passage's exit returns to `main._return_to` when set. Fog of war: `FogMap` (`scripts/fog_map.gd`), saved in `player.explored`; the minimap is `hud._draw_minimap` fed by `main.minimap_info()`. Check with `--headless --path game res://tests/zone_probe.tscn` (`ZONE: PASS`) and `--shot-ui=stubble` / `stubble-cut`.
- **The click tests need a window.** `ui_click_probe` and `creation_probe` push synthetic mouse events through real GUI hit-testing; run with `--headless` the clicks do not land and they FAIL on the first interaction. That, not a bug, was why a sub-agent kept reporting `CREATE: FAIL`. The self-test, the bots and `nether_death_probe` are the headless ones.
- **UI click test** (windowed): `--path game res://tests/ui_click_probe.tscn` and again with `-- --field` must print `UICLICK: PASS`. It drives the inventory with synthetic mouse events (left-click, right-click, drag onto a slot), in town and with the game paused, and (without `--field`) clicks the trainer in the street, Training, a tree node and Learn. Extend it whenever a screen gains a new interaction - a screenshot proves a screen draws, not that it can be used.
- **Script errors fail tests** (`tests/error_catcher.gd`, `ErrorCatcher.install()`): a GDScript runtime error aborts only the function it is in, so a test that checks state afterwards can pass over a real crash (in the editor the same error halts the game). The self-test and `nether_death_probe` count errors and fail on any; new tests that drive gameplay should do the same. `--headless --path game res://tests/nether_death_probe.tscn` (and `-- --hardcore`) must print `NETHERDEATH: PASS`: the whole game, dying to a construct in the Netherecho. Tests that wait for something to happen must wait on game time, not frame counts - a headless run is unthrottled.
- **Rules self-test**: `--headless --path game res://tests/selftest.tscn` must end `0 failed` (exit code 0). It drives wound maths, natural healing, arm loss/regrowth, healer credit and rent directly. Add a check there whenever a rule changes. It is a stopgap until GUT is installed (`/test-setup`), and it proves arithmetic, not feel.

## Collaboration Protocol

**User-driven collaboration, not autonomous execution.**
Tasks follow: **Question -> Options -> Decision -> Draft -> Approval**

- Show a draft or summary and get approval **per changeset** (a story, a doc, a feature) before writing — not per individual file.
- Review mode is set in `production/review-mode.txt` (`full` | `lean` | `solo`).

## Version Control

Standing instruction from Brent (2026-09-19): **keep good version control** — commit as work lands, don't wait to be asked each time.

- **Commit each approved changeset** (a story, a doc, a fix) as its own commit, straight after it is approved and the smoke check passes. Never batch unrelated work into one commit.
- **Conventional Commits**: `feat:`, `fix:`, `docs:`, `chore:`, `test:`, `refactor:`, with a scope where it helps (`feat(game):`, `docs(design):`, `docs(research):`, `chore(process):`). Reference the story/task ID or design doc in the body.
- **Never commit a broken build.** Game changes must pass the headless smoke check first; if something is knowingly incomplete, say so in the commit body.
- **Tags**: annotated tags at every playable build handed to Brent (`vX.Y.Z-<label>`) and at every phase gate passed (`gate/<stage>`).
- **Push**: after each merge to `main`, push `main` and its tags to `origin` (Brent 2026-10-22). Never push worktree or agent branches.
- **Still ask first**: adding another remote, force-pushing, rewriting history (amend/rebase/reset of committed work), deleting branches or tags. Any remote must be **private** unless Brent decides otherwise.
- **Never commit**: book text, anything under `game/.godot/`, credentials.
- Line endings are governed by `.gitattributes` (bash hooks must stay LF).

See `docs/COLLABORATIVE-DESIGN-PRINCIPLE.md` for the template's full protocol.
