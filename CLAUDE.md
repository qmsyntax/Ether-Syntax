# Ether Syntax (working title; was "Passage") — an action RPG inspired by the "1% Lifesteal" universe

Brent's own game, inspired by how the 1% Lifesteal world works and its power system, with the author's informal
blessing (see rule 1). Not a licensed or official adaptation. Process framework: Claude Code Game Studios
template (MIT, see `.claude/LICENSE-ccgs`), adapted. Owner / product lead / lore authority / playtester: Brent.

## Project rules (these override anything in the template)

1. **What we may use.** The series belongs to Robert Blaise (publisher: Aethon Books). Brent asked him, and on
   2026-10-22 he answered (`production/outreach/2026-10-19-robert-blaise/reply-2026-10-22.md`): a game *inspired by*
   the 1% Lifesteal universe is fine, using **how the world works and the power system**; **not** the story or the
   characters. It is not a licence: any official adaptation begins on his side, so never present Ether Syntax as the official
   1% Lifesteal game.
   - Use freely: the world's workings and the power system (stars, essence and reflux, talents and primes, the
     ethercosm and Netherecho, constructs, passages and realms, runes). Lean into setting-faithful tone and mechanics.
   - Never: the story, plot events or canon characters. Player characters, NPCs, talents' wording, names and art are original.
   - Never store, paste or reproduce book text. No bulk downloads, no DRM stripping, no piracy sites. Work from
     paraphrased mechanics notes with chapter citations (`research/`), fan sources, and Brent's recollection.
   - Nothing is published or distributed, and nobody is contacted, unless Brent explicitly asks. Whether the books'
     coined terms keep their names in a public release is decided then.
2. **Provenance tags are mandatory** in design docs: `[C]`/`[CANON]` read directly, `[F]` fan source, `[B]` Brent's ruling, `[MODEL]` our invention, `[?]` unknown. Brent's rulings override fan sources. See `design/01-systems-bible-v0.md`.
3. **Say what was and wasn't tested.** A headless run proves scripts load; it does not prove a mechanic works or feels right. Anything that needs hands on the controls is reported as "untested — needs Brent". Never claim a feature works on the strength of it compiling.
4. **The first real gate is fun, not paperwork.** The core-loop questions in `design/03-core-mechanics-spec-v0.1.md` §8 are answered by Brent playing the build. The author would like to see it; the vertical slice is the natural thing to show him, when Brent says.
5. **Talents are data** (`game/data/talents.json`), many and varied — 1% Lifesteal is one entry, not the premise.

## Technology Stack

- **Engine**: Godot 4.7.2 (standard build, installed via winget — no `godot` alias on PATH; use `open-editor.cmd`, or the console exe under `%LOCALAPPDATA%\Microsoft\WinGet\Packages\GodotEngine.GodotEngine_*\`)
- **Language**: GDScript, statically typed
- **Godot project root**: `game/` (this is `res://`). The template's `src/` and `assets/` conventions map to `game/scripts/` and `game/data/` until `/adopt` decides otherwise.
- **Version Control**: Git, trunk-based on `main`, pushed to the private GitHub repo `qmsyntax/Ether-Syntax` (remote `origin`, SSH). See "Version Control" below.
- **Smoke check**: `--headless --path game --import`, then `--headless --path game --quit-after 400 -- --shot` must produce no `ERROR` / `SCRIPT ERROR` lines.
- **Tuning numbers live in `game/data/*.json`** (`balance.json`, `enemies.json`, `abilities.json`, `talents.json`) and are read through the `GameData` autoload. No numeric gameplay constants in scripts — structural constants (layer names, colours, panel sizes) are the only exception.
- **Damage goes through the hook pipeline.** `Player.deal_damage()` and `take_hit()` build a `HitContext` and run it through every `TalentEffect` in `player.effects` (`on_outgoing`, `on_dealt`, `on_incoming`, `on_reflux_cap`, `on_tick`, `on_ascend`, `status_lines`). A talent is `game/scripts/talents/<id>.gd` extending `TalentEffect`, loaded by id. Items, summons and tempering techniques will be effects too. Never branch on `talent_id` in gameplay code.
- **Interface** lives in `game/scripts/ui/` plus `hud.gd`. `UiTheme` holds the palette, serif font and the Theme applied at `ui_root` (parent of the HUD and every screen); `UiDraw` holds the procedural drawing (orbs, rings, bars, glyph icons); `UiWidgets` the small reusable controls; each screen extends `UiScreen`, owns no game state and calls public methods on `main.gd`. No image assets - everything is drawn. Use `set_anchors_and_offsets_preset`, never `set_anchors_preset`, for full-rect controls (the latter preserves a zero size). Every UI change is verified with `--shot-ui=title|town|town-gate|town-folk|town-talk|skill-tree|skill-tree-field|stations|craft|craft-done|craft-item|shop|saves|inventory|hud|hud-low|hud-dual|temper|ethercosm|nether|create-1..5` (windowed; saves `shots/shot.png`) and `--shot-settings`, and the images are looked at.
- **Character art** is procedural: `game/scripts/art/models.gd` (`Models.player()`, `.enemy(kind)`, `.scenery(kind)`, `.pickup(equippable)`) plus `.weapon(item_id)`, `.projection()`, `.wisp(affinity)`, `.construct(tier, concept)` (`nether_models.gd`), builds `ModelRig`s from procedural meshes (`MeshKit`) - no image or mesh assets. The look is grounded dark fantasy (art pass 3): realistic proportions, muted worn materials, one accent per character; the matching lighting (filmic, SSAO, light fog, low sun) is set in `main.gd` `_build_world` / `_set_nether_look`. The equipped weapon is shown with `ModelRig.set_weapon`. Enemy models are in `art/enemy_models.gd` (grunt, brute, commander, archer, harrier); each has a wind-up pose of its own (the archer's draw, the harrier's crouch) and enemies are fought from behind as well as in front, so backs are designed too. Gameplay scripts own a rig and drive it through `set_highlight`, `flash`, `set_windup`, `set_staggered`, `set_part_visible`, `set_dead_look` and `animate(delta, speed, attacking)` (poses only ease in while `animate` is being called); collision and gameplay sizes still come from data, not from the model. Designs must be original. Preview every model with `res://tests/art_preview.tscn -- --shot` (and `--shot=close`), which saves `shots/art-preview.png` / `art-close.png`.
- **Character creation** is `ui/creation_screen.gd` (steps: Origin, Appearance, Prime, Skills, Embark; a SubViewport turntable in the middle). It builds a draft `spec` {name, identity, look, talent_id, affinities, skills} and calls `main.begin_character(spec)`, which refuses a spec without exactly `skill_tree.json` "start_picks" (2) root skills of the prime's affinities. A look is a Dictionary of option ids; gameplay and UI reach the model library's options only through `CharacterLook` (`options`, `normalize`, `cycle`, `build`), and the options themselves are defined in `art/player_look.gd`. The identity (Man / Woman) sets the look's `sex`, which changes the body and face; options hidden for a sex are listed in `creation.json` `hidden_options`. `set_zoom(close)` frames the face. Identities, name pool and option labels are in `data/creation.json`; affinities and which ones a prime carries in `data/affinities.json` (+ optional `affinities` on a talent). Verify with `--shot-ui=create-1..5` and the windowed click test `res://tests/creation_probe.tscn` (must print `CREATE: PASS`; it picks two skills by clicking and checks nothing else is given).
- **Affinities** (`data/affinities.json`, GENERATED - see "All sixteen affinities" below): water, fire, earth, wind, lightning, ice, dark, metal, blood, life, death, nature, light, dream, poison, disease, each with a colour, a three-ability `kit` (ranged, close, movement), its reflux tier and its rule as text and as data keys. Affinities are NOT tied to the talent (Brent 2026-10-11): they decide which skills can be learned and are rolled per prime. Character creation offers three rolled primes (`PrimeRoll`: talent off a weighted table, 1-3 affinity slots - one common, two rare, three very very rare - each filled at random; numbers in `balance.json` "primes"). `Player.set_affinities` gives the character its affinities and, as a sandbox loadout for tests, shots and bots, their whole kits; a real character then gets exactly its two picked skills from `Player.start_with_skills` (no skill is given automatically - Brent 2026-10-18); `prime_default` (water) is only for tests, bots and old saves. Reflux is per affinity (`reflux_by`, `locked_by`, `reflux_of()`, `is_locked()`); `reflux` / `reflux_locked` are shorthand for the first affinity only. An ability can only be cast if the character holds its affinity. Wisps in the Netherecho carry an affinity and only attuned ones can be gathered. Tint anything affinity-related with `GameData.affinity_color()`. Verify dual-affinity HUD with `--shot-ui=hud-dual`.

- **Skills** (design/05, approved 2026-10-12; step 1 built: water and lightning). A skill's `kind` in `abilities.json` picks its behaviour in `Player.cast_ability`: `projectile`, `melee_burst`, `dash`, `beam`, `targeted_strike`, `blink`. Everything a skill does to an enemy goes through ONE function, `Player.apply_hit(target, payload, tags, stage_mult, dir)`, fed a hit payload from the data (`on_hit` / `on_pass` / `on_arrive`: damage or damage_mult, status, shove, marks, interrupts) - add effects there, never inside a behaviour. Statuses live on the enemy (`add_status`, `status_stacks`, `stun`, `interrupt`, `shove`; rules in `data/statuses.json`). Water shoves, and a shove that ends against a wall, block or body is a Crush (`Player.on_crush`, numbers in `balance.json` "shove"). Lightning leaves Live marks; the third is an Overload (`_add_marks`, `_overload`). Affinity-specific reflux rules are keys on the affinity (`reflux_shed_mult_combat`). Skills that need a target or a landing spot are checked BEFORE essence is spent. A skill has a recovery (`abilities.cast_recovery` or its own) during which nothing else can be cast; running hot lengthens it and no longer hurts. Move things by exact distance (`move_and_collide`, swept checks), not by velocity: `move_and_slide` picks its own time step outside a physics frame, which made a shove overshoot and a dash skip an enemy. Fire is built (step 3a): Heat - an affinity with `damage_per_reflux` multiplies every hit tagged with it by `Player.heat_mult(aff)`, measured at the moment of impact; Alight - a status that burns in the name of whoever applied it (`add_status(id, stacks, by)`), spreads to an enemy that stands close, and jumps on death; a `targeted_strike` may `consume_status`; a `dash` may leave a `trail` (`GroundZone`) and `stops_at_bodies`. The player's dash, like a shove, is moved by exact distance. Wind is built (step 3b): Slipstream - `player.pips`, earned from distance actually travelled (`_tick_slipstream`, numbers in `balance.json` "slipstream") and spent by wind skills (`spend_pips`); Lee - an affinity's `rear_bonus` on a hit to the back; a skill tagged `rear` always counts as from behind; wind's reflux sheds by movement (`reflux_shed_mult_moving` / `_standing`); Aloft status (light enemies only - heavier ones lose poise). Projectiles (`projectile.gd`) fly by exact distance through `tick()`, stop on walls, strike nearest-first and may `pierce`. Earth is built (step 3c), so all five starter kits are: any skill may carry a `windup` - `cast_ability` takes the cost at once, holds the cast in `player._windup` and `_tick_windup` lets it go through `_perform_cast` (the one place a skill's effect happens); you are rooted and aimed until then, and `braced` skills make you Braced (`is_braced`, `balance.json` "braced"). ## Collaboration Protocol

**User-driven collaboration, not autonomous execution.**
Tasks follow: **Question -> Options -> Decision -> Draft -> Approval**

- Show a draft or summary and get approval **per changeset** (a story, a doc, a feature) before writing — not per individual file.
- Review mode is set in `production/review-mode.txt` (`full` | `lean` | `solo`).

## Version Control

Standing instruction from Brent (2026-09-19): **keep good version control** — commit as work lands, don't wait to be asked each time.

- **Commit each approved changeset** (a story, a doc, a fix) as its own commit, straight after it is approved and the smoke check passes. Never batch unrelated work into one commit.
- **Conventional Commits**: `feat:`, `fix:`, `docs:`, `chore:`, `test:`, `refactor:`, with a scope where it helps (`feat(game):`, `docs(design):`, `docs(research):`, `chore(process):`). Reference the story/task ID or design doc in the body.
- **Never commit a broken build.** Game changes must pass the headless smoke check first; if something is knowingly incomplete, say so in the commit body.
- **Tags**: annotated tags at every playable build handed to Brent (`vX.Y.Z-<label>`) and at every phase gate passed (`gate/<stage>`).
- **Push**: after each merge to `main`, push `main` and its tags to `origin` (Brent 2026-10-22). Never push worktree or agent branches.
- **Still ask first**: adding another remote, force-pushing, rewriting history (amend/rebase/reset of committed work), deleting branches or tags. Any remote must be **private** unless Brent decides otherwise.
- **Never commit**: book text, anything under `game/.godot/`, credentials.
- Line endings are governed by `.gitattributes` (bash hooks must stay LF).

See `docs/COLLABORATIVE-DESIGN-PRINCIPLE.md` for the template's full protocol.
